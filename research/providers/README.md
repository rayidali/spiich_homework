# Research provider adapters

These adapters serve the isolated comparative study. They do not replace the deployed Daybook provider, connect to its journals, post transactions, or read credentials automatically. The runner supplies a key and an accounting transport explicitly.

## Public interface

`GeminiResearchClient(key, transport)` exposes:

- `generate({system, prompt, schema, model?, kind?, fileSearch?})`: JSON generation with full local Zod validation. Optional File Search returns provider grounding separately from the generated JSON.
- `searchInteractions({system, prompt, stores, topK?, metadataFilter?, maxOutputTokens?})`: one stateless Interactions File Search request. Returns citation annotations and tool-call/result counts, never generated prose as source evidence.
- `embed(text, {task?, title?, dimensions?})`: a single text embedding, normalized for cosine similarity; default 768 dimensions, `gemini-embedding-001`, separate document/query task types.
- `createStore`, `uploadText`, `importFile`, `pollOperation`, `getStore`, `deleteStore`: explicit managed index lifecycle operations. Upload is two real HTTP requests; polling is a separate caller-controlled operation. No implicit polling loops or cleanup occur.

`JevResearchClient(key, transport)` exposes batched `noul`, candidate `rerank`, and answer `verify`. Jev is pinned to `jev-1.14.0`. Reranking and verification have different request kinds and are separate treatments. `decideJevReview(probabilities, thresholds)` applies explicitly supplied development-calibrated thresholds; a probability is not a guarantee of accounting correctness.

`ResearchTransport` receives the provider, requested model, request kind, URL, headers, JSON body or UTF-8 `rawBody`, and a deadline. It returns status, decoded JSON, elapsed milliseconds and lowercase response headers. A caller can wrap every attempt for persistent budget accounting. The default native transport sends one attempt with no redirects and a maximum 25-second timeout. It allows only the provider's official HTTPS host and bounds request/response size. Tests inject controlled responses; they do not make paid calls.

The adapters return the requested model, returned model version where available, measured request latency and token counts. Unreported tokens are `null`, not zero. Index/control operations do not expose the same token-usage metadata as generation. The runner must account for indexing and unknown usage explicitly; these clients alone are not a billing ceiling. Safe error codes never contain provider response bodies, keys, prompts, or connection URLs.

## File Search comparison boundary

Google's API exposes File Search as a generation tool. It does not provide the same raw scored candidate list as the custom vector retriever. The root agent's live `generateContent` File Search smoke returned an answer without grounding metadata after all 39 authorized documents were indexed. Therefore R3 now has an explicit Interactions adapter, using the current documented API. This is a pre-pilot compatibility amendment, not an automatic fallback that hides a failed request.

The Interactions `FileSearchResultStep` schema exposes a call identifier but no retrieved passage fields. `searchInteractions` returns validated `file_citation` annotations from model-output content, with file name, document URI, source attribution and custom metadata. It discards generated answer text. The caller must resolve those annotations against authorized document records, then supply the original source records to the shared final generator. This is **managed citation selection followed by authorized document lookup**, not raw managed chunk retrieval. `source` is attribution metadata and must not be relabeled as an exact passage. `rawPassagesAvailable: false` makes this limitation explicit. No citations means no evidence; correct-looking prose cannot substitute for citations.

This route costs an additional generation request, which belongs in R3's latency/cost totals. Missing managed chunk boundaries, scores and ranks must be reported as unavailable. The comparison measures the available managed service, not identical retrieval internals across R3 and R4. Interactions requests set `store: false`, use only the trusted File Search store list and bounded `top_k`, request no thought summaries, and reject incomplete/continuation/action-required responses instead of issuing another call. Unknown token usage remains unknown. The budget transport must account for Interactions `generation_config.max_output_tokens` and `usage.total_*_tokens` as well as the legacy generation fields.

Interactions input accounting adds `total_tool_use_tokens` (tool-use prompt context) to `total_input_tokens`. The root's first successful live citation response reported 71 input + 1,871 tool-use + 45 response + 0 thought = 1,987 total tokens. Its `initial_input_tokens: 378` is a first-turn diagnostic and is not added again. Response and thought tokens remain separate: the official REST example reports 80 input + 200 response + 100 thought = 380 total. That example supports charging response plus thought tokens at the output rate; the field descriptions alone do not state an exhaustive billing equation. Cost remains a usage-based estimate, not an invoice reconciliation. Missing base input usage remains unknown even when tool usage is present.

Grounding chunks preserve source URI/title/text, source metadata, optional store and page identifiers, and support-index mappings. A model-produced summary is never silently substituted for a retrieved source passage. Empty grounding is valid evidence of no returned citation; the runner must not invent hits. Missing provider ranks/relevance scores must be reported as unavailable. Grounding with an explicitly different store or invalid chunk indices is rejected.

The runner must select stores from trusted workspace configuration. Metadata filters are retrieval filters, not an authorization system. The study should create an isolated store for each authorized corpus and validate returned document IDs against that corpus. Foreign-workspace documents must never be indexed into an otherwise shared public store as a substitute for access control.

## Sources and pins

Reviewed 2026-10-30 against primary documentation:

- [Gemini generation REST reference](https://ai.google.dev/api/generate-content): `generateContent`, `responseFormat.text`, `FileSearch` tool, retrieved-context grounding and support mappings. The study generator is `gemini-3.5-flash-lite`, normalized across all nine routes before pilot/held-out evaluation. Root-agent smoke attempts recorded repeated 503 responses from 3.1 and successful 3.5 responses; this is an explicit protocol amendment, not a silent per-request fallback. R0 reproduces the current tool architecture with the shared study model; the deployed production model remains 3.1. The critic also uses 3.5 in a separate request, so its mistakes may correlate with the generator. The runner records returned model versions. Array maxima are omitted only from the provider grammar, matching the existing production workaround; the original local schema still enforces them.
- [Gemini embedding guide](https://ai.google.dev/gemini-api/docs/embeddings) and [embedding REST reference](https://ai.google.dev/api/embeddings): `gemini-embedding-001` remains the text model; 768 dimensions are explicit. The root agent's live smoke on 2026-10-30 found the documented nested `embedContentConfig` was ignored: a 768-dimension request returned 3072 values and no usage metadata. The adapter therefore uses the still-documented flat `taskType`, `outputDimensionality` and `title` fields. This is an explicit configuration correction, not an automatic retry/fallback. Input text has a local size bound; the flat interface does not expose a verified no-truncation control. Reduced vectors are normalized locally. Dimension mismatches, nonfinite coordinates and zero norm fail validation; unknown usage remains unknown.
- [File Search guide](https://ai.google.dev/gemini-api/docs/file-search) and [store REST reference](https://ai.google.dev/api/file-search/file-search-stores): separate store creation/import/operations, resumable direct upload, explicit embedding model, and configurable whitespace chunking. Upload requests use 200 tokens per chunk and 20 overlap; the service's tokenizer/chunk boundaries remain managed internals. A returned resumable URL is checked against Google's exact host and upload path before sending document content or credentials.
- [Interactions REST reference](https://ai.google.dev/api/interactions-api) and [official OpenAPI schema](https://ai.google.dev/static/api/interactions.openapi.json): native `POST /v1beta/interactions`; `FileSearch`, `FileSearchResultStep`, `FileCitation`, `GenerationConfig` and `Usage` definitions. The OpenAPI describes custom citation metadata as an object, while the File Search guide shows key/value arrays; both bounded shapes are preserved. Citation segment offsets are UTF-8 bytes, not JavaScript character positions. Resolving provider-supplied file identities against scoped database records remains the caller's responsibility.
- [TypeSafe documentation index](https://docs.typesafe.ai/llms.txt), [System One REST API](https://docs.typesafe.ai/api/system-one), and [model catalog](https://docs.typesafe.ai/models): native `POST /v1/systemone`, bearer authentication, named Noul questions and input/output usage. Jev 1.14's documented price on review was $0.042 per million input tokens, with output tokens free. Pinning the version avoids a silently moving `jev-latest` alias; unexpected returned model IDs fail validation.

Contract tests verify local schema handling, request construction, model pins, vectors, grounding boundaries, upload destination checks, explicit operation errors, Jev probability/answer coverage, threshold decisions, and single-attempt safe errors. Passing them establishes adapter contracts, not live provider compatibility or benchmark accuracy. Those require the runner's recorded live smoke and held-out results.
