# Pre-holdout methodological audit and decision specification

**2026-10-30.** This review inspected source, protocol, and already-known development defects. It did not inspect held-out model outcomes or choose subgroup membership from observed success. The author previously contributed fixtures and scoring; this is an internal engineering review, not independent human adjudication.

The second development pilot stopped at **101/108 recorded attempts** after the Gemini daily quota was reached, according to the runner's checkpoint. No held-out run has begun at this audit. Missing attempts must remain missing; quota exhaustion is not a quality measurement. Runtime changes below were made only after the parent confirmed that the active pilot had stopped. Existing pilot results remain separate and unchanged.

## Blocking findings and resolutions

### 1. The control could not express the shared tag protocol

R0's original adapters initialized empty assumption/clarification tags and returned only prose from its clarification tool and proposal responses. The scorer accepts exact shared vocabulary labels; it does not infer labels from prose. Consequently, a correct request for a missing booking rate could fail the formal rubric regardless of its meaning. This was a real comparability defect, not evidence of poor financial reasoning.

The final development correction exposes the same full assumption and clarification catalogs to R0 within its existing single model response. All four financial tool calls, the existing clarification call, and the proposal schema carry model-emitted metadata. Operational query arguments and accounting scopes remain unchanged, and metadata is ignored by SQL compilation. No new inference, retrieval, critic, or financial tool is added. Missing legacy metadata defaults to empty and earns no inferred credit. Wrong tags remain wrong; no per-question reference label is supplied or copied into the answer.

The baseline provenance now states that this is a normalized measurement schema reproducing the production architecture, rather than claiming byte-identical tool contracts. Nine targeted tests cover the complete catalogs, actual shared-scorer behavior, absent/wrong tags, proposal metadata, model-emitted assumptions, unchanged SQL arguments, and the safety-behavior limitation below. Those tests plus the baseline/validation suites passed **37 tests**, and TypeScript validation passed at 18:48:34 local time. This is offline verification; a successful live smoke of this final version remains pending available provider quota.

Because the baseline source changed, a route-only capability amendment is insufficient. The external subgroup analyzer now requires an explicit reviewed amendment binding **both** baseline and route source hashes while preserving membership. It cannot waive a changed question source. Sixteen subgroup-analysis tests and TypeScript validation passed at 18:49:49. The [final exact-hash amendment](common-capabilities-amendment-v3.json) is now recorded after the parent confirmed the final route edits. It binds both changed files while retaining the original membership and unchanged question hash.

### 2. No run may be called confirmed while coverage or integrity is incomplete

The held-out runner requires the development-selected reviewer calibration to be rebound to the exact final source hash and preserved development inputs/results. It rejects stale source/configuration manifests on resume. Full scoped ledger, documents, and embeddings are fingerprinted before/after evaluation. The original source/data must remain unchanged across a run; a corrected implementation receives a new version.

A negative validity notice can supersede a report's original mechanical completeness flag. The initial pilot's notice is such a case. External subgroup reporting now binds that notice to the original results digest and forces diagnostic status. Invalid or incomplete measurements cannot be rehabilitated by a favorable graph or by recomputing a partial average.

Before any held-out claim: finish and verify a run under the final source, retain every error and missing attempt, confirm matching fingerprints, preserve all requested routes/questions/repeats, and apply any validity notice. The current quota stop is an operational blocker to those measurements, not permission to present the completed subset as the planned experiment.

## Findings that limit interpretation, rather than invalidate the code

**CLARIFY is not BLOCK in R0.** The existing R0 clarification interface always produces formal `CLARIFY`, even if its prose refuses an unsafe action. The measurement normalization does not add a new blocking tool. A strict expected-`BLOCK` rubric can therefore penalize a safe refusal. Report this as a behavior-protocol limitation; it is not evidence of harmful acceptance, a write, or disclosure. Do not convert formal behavior mismatches into a security-incident count. The common-answerable subset excludes such tasks but the primary whole-benchmark score retains them transparently.

**Tag success does not establish prose faithfulness.** `scoreEpisode` records `narrativeReviewed: false`, leaves human clarity and the combined 100-point score unavailable, and can accept correct tags alongside poorly worded or contradictory prose. The generated report and narrative correctly describe structured task success and automated scores out of 90. Preserve those qualifiers everywhere; neither the generation model nor the production critic is an independent human judge.

**No provider-visible label leak was found in the inspected paths.** `providerQuestion` exposes question text, trusted organization, date, and base currency. It omits group/split/labels. R0 receives the question and permitted chart/history. Review stress inputs are explicitly projected and strictly parsed before provider use; expected decisions and fault types remain evaluator-side. Freezing hashes the reference cases but does not send that hash input to providers. The stress evidence intentionally supplies an authoritative one-claim result: that measures review against supplied evidence, not upstream discovery of financial truth. Repository maintainers can still inspect labels, so this is not an externally secret benchmark.

**Same-model critics and separate retrieval paths are imperfect controls.** R7 uses another invocation of the same Gemini weights. R3 uses managed citation-selected sources rather than exposed raw passages/ranks. R4/R5 independently execute the same planner configuration, so stochastic differences in their generated retrieval query can change candidate pools; the comparison measures the route configuration with optional reranking, not a perfectly paired reranking of identical cached candidates. Preserve per-family and paired uncertainty, and avoid claiming algorithmic isolation beyond what was held fixed.

**R6 evaluates a restricted integration.** Its actual Wren engine is pinned, but monetary-unit provenance fails closed on unsupported complex query lineage. This is a limitation of this integration. SQL grammar/column corrections made during development must be disclosed; they do not justify statements that Wren inherently cannot execute those analyses.

**Model repetitions are not independent scenarios.** The full held-out set has 30 scenario groups and five per family. The shared-capability subset has only six groups, two represented families, and 12 questions. Bootstrap resampling keeps paraphrases/repeats together, but estimates can remain unstable or degenerate, and all intervals are unadjusted. The shared small ledger/corpus may introduce dependence even across groups.

**Operational conditions affect cost and latency.** Route order rotates within question blocks, and generation pacing/deadlines are shared. Requests still occur at different times and consume different numbers of calls. Queue delay and daily quota behavior are part of the observed harness environment. Unknown usage remains reserved, not zero. Provider-duration summaries must use per-call usage completeness rather than a legacy aggregate that replaces missing durations with zero.

**Security coverage must be described precisely.** The observed 57-pass/3-unassessed component suite is not the originally proposed execution of all 60 natural-language security cases through every route. Main adversarial episodes and database permission checks provide additional evidence, but do not erase that scope gap. A full nine-route security-study claim remains unavailable unless that work is actually completed. Zero observed violations in a small sample is not a production safety guarantee.

## Concrete proposed final decision rule

This specification applies the existing preregistered five-percentage-point practical threshold, hard gates, verifier false-rejection limit, and quality/cost/latency comparison. It should be accepted and recorded before opening held-out outcomes. It does not introduce a favorable post-hoc weight or select a winner from development scores.

1. **Eligibility first.** Require the complete held-out run, the exact frozen final source/configuration, matching full data fingerprints, valid source-membership amendments, and no overriding validity defect. Disqualify a route from deployment consideration for an observed unauthorized write, cross-workspace disclosure, accepted invalid posting, or permissions bypass. Missing observations or known measurement defects yield “inconclusive,” not an inferred winner.
2. **Keep whole-benchmark macro success primary.** Show all six family rates, errors, common-answerable results, paired differences, and uncertainty beside it. A secondary subgroup or alternative dashboard weighting cannot replace an unfavorable primary result.
3. **Evaluate the declared component comparisons.** For broad analysis and Wren (H1/H6), use the financial and analytics families as the targeted capability summary. For document retrieval/reranking (H2–H5), use documents and scenario families. Report entry and adversarial effects separately rather than moving families into a favorable subset afterward. These family mappings are proposed now from the components' responsibilities, before held-out results.
4. **Require a practical benefit to justify extra complexity.** A query/retrieval component becomes a candidate to keep only with at least **+5 percentage points** in its fixed targeted-family macro success versus its declared control, no hard-gate regression, and no evidence that apparent benefit is merely an invalid measurement artifact. If its interval spans both useful improvement and material harm, describe the result as inconclusive and keep the simpler product configuration pending more data; do not present an unadjusted interval as a significance test.
5. **Apply the verifier criterion separately.** Against the shared deterministic stress control, require lower operational acceptance of flawed candidates and no more than **+5 percentage points** of additional withholding of correct candidates. Show conditional semantic rates and request errors separately so network failure is not credited as flaw detection. Also show R7/R8 versus R4 on complete end-to-end task success. A reviewer that improves a contrived stress set while substantially harming useful task completion has not earned an automatic product recommendation.
6. **Resolve tradeoffs visibly.** Among eligible candidates, remove configurations dominated on targeted/overall success, provider error rate, p95 harness latency, and paid-equivalent cost per successful task. For remaining tradeoffs, show the additional successful tasks, calls, latency and cost rather than inventing a universal “best” score. When observed quality gains are below the preregistered +5-point target or evidence is inconclusive, prefer the configuration with fewer services. Do not deploy an unmeasured combination of favorable components.
7. **Make the final recommendation proportional.** With only small synthetic samples and no independent human prose/reference adjudication, “candidate for the next product experiment” is stronger evidence than available for an unconditional production reliability claim. The existing application can remain unchanged even if a research route looks promising.

The five-point values above come from the plan. No new hidden dollar cap, latency cutoff, or statistical significance threshold is introduced. If the product owner wants a strict latency/cost ceiling, it must be written before interpreting held-out results, not selected to favor a measured route.

## Prespecified secondary weight-sensitivity design

The plan promises sensitivity to reasonable weight changes. The frozen runtime currently reports the single 40/20/20/10 automated rubric; it does **not** implement a sensitivity table. This can be generated externally from the preserved component scores without another provider call or changing primary task success.

For each episode let `F = factual/40`, `C = completion/20`, `G = grounding/20`, and `U = uncertainty/10`. Compute `wF×F + wC×C + wG×G + wU×U` for the following fixed alternatives, each totaling **90**. Never infer or impute the unavailable human dimension.

| Secondary weighting  | Factual | Completion | Grounding | Uncertainty | Purpose                                                  |
| -------------------- | ------: | ---------: | --------: | ----------: | -------------------------------------------------------- |
| Original             |      40 |         20 |        20 |          10 | Preserve the preregistered dashboard                     |
| Financial emphasis   |      50 |         15 |        15 |          10 | Increase the cost of wrong financial facts               |
| Evidence emphasis    |      30 |         15 |        35 |          10 | Increase the importance of provenance                    |
| Uncertainty emphasis |      30 |         15 |        20 |          25 | Increase the importance of assumptions and clarification |
| Equal dimensions     |    22.5 |       22.5 |      22.5 |        22.5 | Check dependence on unequal dimension weights            |

The later external table should show one row per route, five out-of-90 means, per-family values, and the minimum/maximum rank across weightings. Use equal family weighting for the full benchmark; unavailable families remain unavailable. Provider errors retain their recorded zero component scores, blocks retain their actual graded components, and route hard gates remain disqualifying independently of any score. Missing planned episodes remain explicit and prevent a completed-study conclusion.

This is a robustness description, not a new selection objective. Do not choose whichever column favors a preferred component, average columns into a new “overall winner,” or claim that stable ranks certify factual prose. Record the analysis specification/hash before applying it to held-out data, and carry original input/result hashes plus any validity notice into the supplemental output. The fixed specification was then implemented in [scripts/analyze-weight-sensitivity.ts](../../scripts/analyze-weight-sensitivity.ts), outside the inference runtime. Seven provider-free tests verify normalization, rank reversals, error denominators, missing-family handling, hard gates, notice binding, and malformed-score rejection. Together with the subgroup and R0 metadata suites, **32 tests passed**, followed by TypeScript validation at 18:55:06 local time.

The tool generated [initial-pilot diagnostics](../evidence/research-runs/pilot-v1/sensitivity/report.md) and [second-pilot diagnostics](../evidence/research-runs/pilot-v2/sensitivity/report.md). Both remain explicitly ineligible and show no ranks. No held-out outcome was used or generated. Output provenance hashes the fixed weights, analyzer, original report, and validity notice. A later held-out analysis must use the same weights rather than select a favorable column.
