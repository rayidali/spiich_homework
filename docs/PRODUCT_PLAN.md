### Explicit expense scope safeguard — deployed with limits

The deployed guard recognizes supported standalone first-user expense questions with no earlier user turns, resolves an exact unique account name/code, and expands groups to effective authorized posting accounts. It compares identities, net posted base-currency expense semantics, grouping, filters and optional explicit ISO dates in the **same repeatable-read execution snapshot** used for the financial read. Complete equivalent descendant selections can pass; matching dollar amounts alone cannot. The result exposes original-user spans and exact `checkedFields`. Without supplied dates it explicitly leaves the selected period unproved.

Wrong scope is withheld before reading amounts, without rewriting or retrying the plan. Unknown explicit codes, duplicate names and noun shorthand that could identify a different account require clarification. The planning chart can only veto a known identity that disappears; positive proof always uses the execution snapshot. A merchant name unknown in both charts remains unassessed and retains the ordinary vendor-query path, without a verification claim. Adversarial offline regressions and the 12 passing PostgreSQL cases cover these boundaries. [Verification](VERIFICATION.md#expense-scope-guard--ci-verified-and-deployed).

Next, design similarly explicit contracts for compositional account/vendor/date constraints and follow-ups that retain or deliberately replace earlier scope. This guard does not resolve that meaning: any earlier user turn makes it unassessed, even when the latest question looks complete or asks to reset. Assistant-only preambles are eligible. Ordinary execution still receives every accepted message, but gets no proof from this guard; retaining context alone does not prevent a dropped prior constraint. Arbitrary vendor clauses, negation, comparisons, multi-part questions and general formula choice remain outside its grammar. Do not label unrecognized requests verified or broaden the recognizer without contrast cases. No new provider cohort, generalized accuracy claim or reassignment of an old score is implied.

## Immediate design decisions

- Error references are tracking numbers, not saved copies of private conversations. Start with safe structured runtime logs. Add Sentry or another service only if the evidence shows the existing runtime-log workflow is inadequate; the user offered access if needed.
- A reviewed posting is the learning boundary. Saving a draft alone does not teach the model. The server stores its own structured proposal and validates the entry binding; arbitrary client-supplied examples are not trusted.
- Posting and recording a meaningful correction are one database transaction. The interface must not claim that a choice was remembered after a separate hidden failure.
- Automatically resolved anomaly alerts retain their history and reason. They are not silently deleted or labeled as user-dismissed.
- Keep numerical accounting in exact deterministic code. Models propose accounts/meaning and ask questions; they do not bypass posting validation or user review.
