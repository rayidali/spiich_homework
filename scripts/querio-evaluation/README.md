# Querio development evaluation specification

This directory specifies **eight selected cases / ten user turns** for an actual Querio evaluation and supplies a pure SQL fixture exporter. The live connection, observed failures, subsequent attempts and their review belong in the [Querio evaluation report](../../docs/QUERIO_EVALUATION.md). The selected cases are already known to the developers. This is neither a blinded holdout nor the full 22-case generated-analysis suite or combined 53-case application acceptance.

`acceptance.ts` contains expected answers and review rules. Importing it or generating fixture SQL makes no provider call and establishes no model accuracy result. Keep the specification separate from what a particular run actually demonstrated. The report preserves the first attempt's session failures and documents the later use of a fresh execution environment for each case. A separate default-model diagnostic must retain its own scope and results; it must not be combined with the eight-case economical-model cohort or reported as an overall model winner.

The original F case IDs, questions and numeric expectations are reused unchanged from `../flexible-analytics-evaluation/specification.ts`. The data comes from that directory's `fixture.ts`: fictional balanced journal entries, including refunds, empty months, a draft, another workspace and a future posting. The historical live demo amounts are not this fixture's amounts. The actual user’s rent wording is reused to test the same conversation problem against known answers.

## Fixture export and live validation

`fixture-export.ts` exports `exportQuerioFixture(options)` and `querioFixtureRecords()`. The exporter returns SQL, ordinary accounting context, a manifest with deterministic hashes and separate operator verification queries. It does not connect to PostgreSQL, call Querio, read credentials or run the SQL itself. Its SQL checks the exact dedicated database name before mutations, requires an empty database, creates fresh schemas and a restricted `NOLOGIN` reader, and checks that every seeded entry balances. Credentials and the operational API controller are not part of this public module.

The generated fixture was materialized in a **separate Neon database**, preserving all **48 entries / 96 lines / 12 accounts / two workspaces** from the native fixture. It is a disposable accounting-data copy, not a migration of Daybook's production schema. The primary workspace is exposed through four views:

| View                | What Querio can read                                                                                                                                 |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ledger_lines`      | Primary-workspace journal lines, including account, date, counterparty, status, native debit/credit, recorded exchange rate and stored base amounts. |
| `chart_of_accounts` | The primary workspace's six accounts and their accounting types/cash classification.                                                                 |
| `calendar_months`   | A calendar scaffold for retaining quiet months; it contains no financial answers.                                                                    |
| `workspace_context` | The base currency and fixed business date, November 3, 2026.                                                                                         |

Actual reader checks returned **47 visible entries / 94 lines / six accounts**, including one draft. The other workspace's entry remains in private storage and is hidden from these views. The reader could select the ledger view, but could not access the storage schema, write the ledger, create schemas or temporary tables, or create objects in the reader schema. Its default transaction mode was read-only. Draft rows remain visible deliberately: the generated query must select `POSTED` for recorded financial answers. The fixture contains only USD with exchange rate 1; it supplies no foreign-exchange performance evidence.

Verification has two distinct layers. **Twenty offline tests** check export fidelity, balance, deterministic identities, SQL identifier rejection, isolation/grant structure and the absence of expected answers in model context. Separately, an independent Python audit performed **2,971 checks over captured records from the live fixture**, using exact `Decimal` and `Fraction` arithmetic without the product calculator. It checked stored fields and relationships, all 48 balanced entries, totals, and all 32 expected final output rows against the separately authored oracle. These are fixture-validation checks, not 2,971 model questions or live database queries. Live privilege checks and pre/post ledger fingerprints are separate evidence.

The service receives accounting definitions and the scoped views, never this README's answer table, acceptance review rules or oracle output. This semantic presentation differs from Daybook's checked query compiler and must be disclosed in any comparison. Neither a validated fixture nor a read-only role proves that an agent chose the correct formula or explained its result accurately.

## Keep the comparison fair

Before sending questions, freeze the actual source, fixture, selected case specification, datasource schema/views and service configuration. Independently reconcile the materialized database against the original fixture: 2025 rent $1,200, net expenses $2,050 and revenue $6,000; 2026 through November 3 rent $350, expenses $600 and revenue $1,500. Verify the stored rows and isolation sentinels, not just the totals. A correct total can hide two incorrect rows that cancel.

Use a fresh conversation for each case. Within F01, send each fixed user turn after the actual preceding assistant response, preserving that response even if it was poor. Do not replace an awkward clarification with a scripted successful one. Set the business date to **2026-11-03** through ordinary context or a recorded service setting. Do not expose this file, expected answers or grader hints to the model.

Provide ordinary accounting definitions: net expense is expense-line debit minus credit; base currency is USD; posted entries only; tenant is the fixture's primary workspace; Rent is 5010 and Marketing is 5030. Record precisely what schema and semantic help Querio received. Curated views are allowed, but a view containing the answer to a test question would change what is being tested. If native Daybook and Querio receive different semantic assistance, disclose that difference; this is a product-path comparison, not an isolated model benchmark.

The independent answers originate in the retained Python `fractions.Fraction` and `decimal.ROUND_HALF_UP` oracle, which imports no application calculation code. Reusing it keeps the numeric comparison compatible with the native route. The fixture is also built from those authored values, so checking the independently materialized database remains essential. Neither Daybook's calculated output nor Querio's explanation becomes the grading oracle.

## Three separate checks

**Numerical correctness:** compare every required number or undefined outcome with the oracle after identifying its label, unit and period. Missing rows fail completeness; zero is not equivalent to undefined. Default reported amounts and percentages round to two decimal places using the declared rule. A correct number next to the wrong month fails. Check every additional displayed financial figure too. Record correct, wrong, missing and unverified counts; clarification-only turns have no numerical score.

**Semantic completeness:** independently read the whole conversation. Did it answer the actual question, calculate percentages rather than merely list their ingredients, keep the intended denominator, and carry context forward? Did it explain zero division without inventing a cause? F03 and F04 deliberately have different answers: averaging monthly percentages is not the same as dividing the year's totals. A valid query and a friendly answer do not establish these properties.

**Query and scope proof:** retain actual executed SQL, bound parameter values, returned rows, errors and any later calculation. Prove the primary workspace, posted status, dates, correct account side, signed refunds and grouping grain. These constraints may be enforced in an inspected view rather than repeated in every query. Review view definitions and join cardinality; do not grade SQL with a simple substring match or require one particular SQL spelling. If a needed query or downstream calculation is unavailable, mark that evidence unverified. Matching the expected answer by coincidence is insufficient.

F14 illustrates why SQL inspection matters: the numerator must filter both Marketing and `counterparty = 'Alpha'`, while the denominator must include all counterparties and expense accounts. This unchanged fixture has Alpha and Beta but no Alpha-like decoy. Therefore the numbers cannot distinguish equality from `LIKE 'Alpha%'`; the actual predicate supplies that proof. A future decoy test must be a separately versioned fixture, not silently inserted into this compatible comparison.

A **whole conversation pass** requires every turn's semantic checks, all required outcomes, supported extra financial claims, verified scope/formula and an unchanged ledger. Report each dimension separately as well. Preserve original failures, partial runs, unavailable evidence and later adjudications. An API error or unsupported operation is not a removed test. No automatic overall scorer or live runner is supplied by this specification.

## Evidence and boundaries

Use only a disposable fixture database and restricted read-only credentials for the service. Retain pre/post fingerprints of all fixture journals, lines, accounts and organizations. Save private raw transcripts and query receipts with source/datasource binding; publish only sanitized results. The acceptance module contains no API client, token handling, network access or database mutations.

This initial set is intentionally small enough to discover integration and answer-quality problems before a larger run. Do not turn an eight-case result into “perfect accuracy,” general superiority over Gemini, a fresh score for the full native suite, or evidence that hosted Daybook has changed. Any native comparison still needs an actual result bound to the same selected cases, fixture and candidate; past results on other questions or source versions are not a paired baseline.
