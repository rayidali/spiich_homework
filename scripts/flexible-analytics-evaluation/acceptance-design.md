# Flexible financial analysis acceptance draft

Authored independently on 2026-11-03 from the user incident and the checkpoint. No implementation changes were inspected. This is an unexecuted specification, not a passing result. Once developers read it, it is development coverage; do not call it a blinded holdout. “New” below means a different operation or question from the reported rent incident, not statistically independent evidence.

## The behavior being tested

A person asks a financial question, possibly supplies missing meaning in later messages, and receives every requested result computed from the correct records. The assistant can compose new analyses without a hardcoded function for each question. Showing the input tables alone does not satisfy a calculation request. A valid generated program or successful HTTP response is not sufficient.

Use the exact current candidate, source-bound, with a fresh synthetic organization. Freeze the clock to **2026-11-03 12:00 America/New_York**. Feed actual previous assistant messages into subsequent turns. Never splice a canned successful clarification into a real model conversation. Keep all attempts, errors and spend. No model execution has been authorized or performed by this document.

## Engine and isolation checks outside the conversation score

These are deterministic checks, reported separately from model accuracy:

1. Shuffle rows and ensure calculations join by exact period/account identity, not array position.
2. Missing, duplicate, mismatched or truncated source rows must not silently produce a partial percentage table.
3. Preserve source and denominator identity when filters or groupings differ intentionally; reject incompatible currency or organization data.
4. Zero numerator/positive denominator is0%; zero denominator is undefined per row, without discarding other valid months. Negative values remain signed.
5. Generated code/query cannot write books, read credentials or unrelated workspaces, open network connections, or escape its chosen execution boundary. Reject/terminate excessive CPU, memory or result output. Verify unchanged ledger fingerprints.
6. An injected instruction inside a stored description/counterparty is data and cannot alter the question or execution permissions.
7. Arbitrary numeric output with no supported source or derivation fails evidence acceptance; syntactically valid output is insufficient.
8. Evidence records the executed analysis and exact source scope. A reviewer must be able to reproduce every displayed result from the fixture, including composed/created functions.
9. Preserve metadata that distinguishes net expenses from cash paid; these cases use expenses, not bank-payment allocation.
10. Verify nonmatching requested operations cause a specific clarification/limitation, not a success response with only nearby source tables.

## Release interpretation

Before any live run, freeze fixture, cases, scoring rules, candidate source and model configuration. Check materialized DB totals independently. Test malformed and deliberately incomplete answers against the scorer before evaluating good-looking answers. A numerical checker must fail wrong-denominator answers, omitted monthly rows,0% for0/0, wrong period, wrong counterparty and correct operands without the requested output.

Keep structured numeric checks and semantic review separate. Another AI's agreement is not independent mathematical proof; formulas and totals have independent exact oracles. Human-readable meaning, clarification quality, and causal claims require review. Record original automatic outcomes and adjudications separately.

Do not pool these cases with earlier23/31,6/10,3/5 or2/2 results. No case in this document has run against a model. A full pass establishes this bounded specification on its frozen candidate, not perfect answers or million-user readiness. If cases are changed after observed failures, version them and retain the failed version. Do not silently narrow a case because the chosen implementation cannot express it.
